## Sources and established practices

1. [PostgreSQL 17 explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html) — `SELECT FOR UPDATE` locks **existing** rows, not absent singleton keys; consistent lock ordering avoids deadlocks.
2. [PostgreSQL 17 INSERT / ON CONFLICT](https://www.postgresql.org/docs/17/sql-insert.html) — unique constraint/UPSERT is the arbitration mechanism for concurrent first insert.
3. [PostgreSQL 17 CREATE TRIGGER](https://www.postgresql.org/docs/17/sql-createtrigger.html) and [TRUNCATE](https://www.postgresql.org/docs/17/sql-truncate.html) — row UPDATE/DELETE triggers do not intercept TRUNCATE; statement-level TRUNCATE trigger and privileges are separate.
4. [PostgreSQL 17 COPY](https://www.postgresql.org/docs/17/sql-copy.html), [jsonb](https://www.postgresql.org/docs/17/datatype-json.html), [MVCC isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [privileges](https://www.postgresql.org/docs/17/sql-grant.html) — transactional COPY FROM STDIN and jsonb storage are viable; count-only verification does not establish payload integrity; READ COMMITTED is viable only with explicit serialization protocol.
5. [GitHub: pressly/goose](https://github.com/pressly/goose) (versioned migrations), [GitHub: jackc/pgx](https://github.com/jackc/pgx) (CopyFrom), [GitHub: golang-migrate](https://github.com/golang-migrate/migrate) (alternative migration workflow). These confirm tooling choices, **not** an implementation of this exact content registry. [Hysen Labs projects](https://hysenlabs.com/projects) consulted for immutable content/versioned deployment patterns; a directly comparable, verified reference implementation **not found/verified**. The directory is not evidence that active-pointer semantics are correct. Specific project tags/security not reaudited for this review.

## Focused review by requested area

1. **Stage/publish/rollback:** R-01, R-03, R-04. `READ COMMITTED` is **sufficient only with correct singleton serialization, conflict detection and lock ordering**, not from the present prose alone. First-publish and rollback races need explicit tests.
2. **Immutability:** R-02 and R-09. Triggers are not a privilege model. A superuser/table owner can change triggers; application should not be owner. `TRUNCATE` is not caught by row DELETE trigger.
3. **Schema, 4925 entities:** R-10. `CHECK(manifest_sha256=build_id)` is a valid invariant, not cryptographic proof of the stored manifest or payload. `COPY FROM STDIN` in a transaction is appropriate; benchmark before choosing it over batched INSERT. Retention/GC must respect live references.
4. **Export:** R-05, R-06, R-07, R-12. Exporter uses `sort_keys=True, ensure_ascii=False, separators=(',', ':')`, sorted `(kind,id)`, UTF-8 LF and trailing newline. Cross-language byte identity and malformed JSON defenses remain unproven. Producer schema_version=1 is fixed; future changes require version negotiation.
5. **Rollback and live instances:** R-08. Keep pinned build immutable; never run schema DOWN for content rollback. Future EX-P04 FK must be decided before GC.
6. **goose:** R-11. Four proposed sequential migration files, no `NO TRANSACTION` currently needed, `Down` dev-only. Verify advisory locks in exact goose tag and concurrent migrators in live PostgreSQL; **not tested**.
7. **Cross-contract/canon:** R-06/R-07/R-08/R-11. `toolchain-pins` documents Go 1.25 for server and Go 1.26 auto for goose; these are compatible *if separated*. Canon §14's sample `kind=main_quest` vs export `quest_main` is explicitly an illustrative example; still document mapping, do not silently assume exact string match.

This is sound **for producer-generated inputs**, subject to strict loader verification.

These are **tests in source**, not tests executed in this session.
- [db-content.md:55–61](../contracts/db-content.md) separates stage from pointer flip and specifies atomic publish and content-only rollback. The design is correct in principle if R-01/R-03/R-09 are resolved.
