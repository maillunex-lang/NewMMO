## Research-first (до кода)
Найди проверенные паттерны для маленького Go-HTTP-сервиса (конфиг из env, health/readiness, graceful shutdown, структурные логи): **GitHub**, **каталог Hysen Labs https://hysenlabs.com/projects**, официальная документация Go (net/http, log/slog, os/signal, context). Сравни ≥3 варианта (напр. чистый stdlib; chi; echo/gin; готовые health-библиотеки) по лицензии, активности, размеру зависимостей, пригодности для авторитетного MMO-сервера на WebSocket (EX-P04/P05). Запиши `docs/research/T-005-go-service-baseline.md`. **Ничего не ставить**; в этой задаче реализуешь только на stdlib. Если считаешь, что нужна зависимость — запиши как предложение (владелец решит).

## Цель
Усилить dev-сервер, не меняя его роль (пока это заглушка без БД).

## Что сделать (stdlib only)
1. Конфиг из окружения: `NEWMMO_ADDR` (по умолчанию `127.0.0.1:18086`; старую `PORT` поддержать как обратную совместимость). Слушать по умолчанию только loopback.
2. `/healthz` — как сейчас (поле `ok`, `service`, `time`), контракт не ломать. Добавить `/readyz`: 200 когда готов, 503 при shutdown.
3. Graceful shutdown по SIGINT/SIGTERM с таймаутом (`http.Server.Shutdown`), таймауты чтения/записи (защита от slowloris).
4. Структурное логирование через `log/slog`, middleware с request-id и временем ответа; не логировать секреты.
5. Код разнести минимально: `server/main.go` (запуск) + `server/internal/...` по необходимости; без глобального состояния; тестируемые функции.
6. Тесты (`httptest`): healthz контракт, readyz 200/503, shutdown, конфиг (env/PORT), middleware. `go vet ./...` и `go test ./... -race` зелёные.

## Не делать
