# T-018 — Пароли, одноразовые билеты и лимиты входа

Проверено 2026-11-21. В GitHub проверены Go и Go Crypto, их лицензии и активность. Поиск в Hysen Labs по `go authentication`, `go rate limit` и `argon2` показал Djoser и Node Argon2, а карточка pgx подтвердила применимость существующего PostgreSQL-драйвера. Djoser требует Django/Python, Node Argon2 — Node.js. Эти варианты потребовали бы отдельного стека. [Каталог](https://hysenlabs.com/projects) · [Djoser](https://hysenlabs.com/projects/sunscrapers-djoser) · [Node Argon2](https://hysenlabs.com/projects/ranisalt-node-argon2) · [pgx](https://hysenlabs.com/projects/jackc-pgx)

| Вариант | Лицензия, активность и применимость |
|---|---|
| Go stdlib, PBKDF2-HMAC-SHA256 | Выбран D-004. BSD-3-Clause, push Go 2026-11-21, 0 внешних модулей. OWASP приводит 600 000 итераций для PBKDF2-HMAC-SHA256. Формат хранит число итераций, соль 16 байт и результат 32 байта, чтобы повысить стоимость при успешном входе. [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [Документация PBKDF2](https://pkg.go.dev/crypto/pbkdf2@go1.25.0) · [Go на GitHub](https://github.com/golang/go) |
| Argon2id из Go Crypto | BSD-3-Clause, push 2026-11-15. OWASP рекомендует Argon2id для общего случая; он требует настраиваемую память на запрос. Для T-018 понадобился бы импорт из внешнего модуля и изменение формата D-004. [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [Argon2 на GitHub](https://github.com/golang/crypto/tree/master/argon2) |
| bcrypt из Go Crypto | BSD-3-Clause, push 2026-11-15. OWASP рассматривает его как вариант для унаследованных систем. Go bcrypt ограничивает пароль 72 байтами, тогда как D-004 разрешает до 128 символов Unicode. Понадобились бы внешний модуль и другая парольная политика. [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [bcrypt на GitHub](https://github.com/golang/crypto/tree/master/bcrypt) |

В предполагаемой реализации сравнение 32-байтовых производных ключей выполняется через `subtle.ConstantTimeCompare`. Неизвестный логин проходит PBKDF2 с текущей стоимостью и возвращает тот же ответ 401, что и неверный пароль. Для access-токена и WS-билета используется `crypto/rand` на 32 байта. PostgreSQL получает хеши, а клиент получает значения только при выдаче. [crypto/subtle](https://pkg.go.dev/crypto/subtle@go1.25.0) · [crypto/rand](https://pkg.go.dev/crypto/rand@go1.25.0) · [D-004](../contracts/auth-session.md)

Для билета подходит условный `UPDATE … RETURNING` по хешу, сроку и отсутствию отметки потребления. Под READ COMMITTED второй конкурентный UPDATE ждёт первый, затем PostgreSQL пересматривает условие и второй запрос получает ноль строк. Для лимитов и аккаунта требуется общий для процессов счётчик и сериализация проверки с записью, иначе одновременные запросы могут пройти один и тот же порог. Локальный token bucket в Go удобен для сглаживания нагрузки, но сам по себе не хранит общее скользящее окно из D-004. [PostgreSQL UPDATE](https://www.postgresql.org/docs/17/sql-update.html) · [READ COMMITTED](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED) · [Go token bucket](https://pkg.go.dev/golang.org/x/time/rate)

## Решения по реализации

- NFC выполняется внутри Go-процесса через уже закреплённый `golang.org/x/text v0.41.0`. В Go 1.26.11 публичного stdlib API NFC нет. Прямой импорт согласован, состав и версии модулей сохраняются. [D-004 §1](../contracts/auth-session.md#1-credentials) · [API NFC](https://pkg.go.dev/golang.org/x/text@v0.41.0/unicode/norm)
- При создании персонажа сохраняется nullable FK `characters.content_build_id` на опубликованный активный билд. До первой публикации сохраняется NULL. [D-004 §4](../contracts/auth-session.md#4-character-creation-initial-state) · [Контракт указателя](../contracts/db-content.md)
